# Planned Release [0.1.1]

# 0.1.1 — qjs Async Concurrency (goroutine-safe Promise resolution)

## Problem

The current JS bridge (`packages/coding-agent/src/core/extensions/js_context.go`'s `buildJSUI`) wires `ui.input` / `ui.select` / `ui.confirm` / `ui.editor` using a **synchronous body** pattern: the async function blocks the JS runtime thread until the Go widget call returns, then resolves the Promise. This is the workaround for a fundamental limitation in `github.com/fastschema/qjs` v0.0.6.

### The underlying issue

`fastschema/qjs` is QuickJS compiled to WASM and run via wazero. QuickJS is single-threaded; WASM has no real threads. The library does not expose a thread-safe "post a job to the runtime" API. Calling `this.Promise().Resolve(...)` from a goroutine while another goroutine is inside `Eval` / `Await` crashes with:

```
panic: failed to call QJS_Call: wasm error: unreachable
```

The library's own `proxy_test.go:540` uses a goroutine pattern with `time.Sleep(10ms)` to let the main goroutine reach a safe "awaiting" state first. That timing-dependent workaround is not robust enough for production — user input can take 30+ seconds, far longer than any sleep.

### Current workaround

Synchronous body. The async function blocks until the Go call returns. This works because:
- The TUI runs on its own goroutine and stays responsive
- Extension handlers are sequential by design
- The WASM runtime is never reentered while running

It covers the realistic extension use cases (event handlers, UI prompts, slash commands). What it does **not** cover:

- Background timers / intervals in JS (would need to wake the runtime)
- A JS extension spawning a worker goroutine that reports back via Promise
- Long-running CPU work in a handler that should yield to let other JS run
- Concurrent extension handlers (one blocks the others)

## Planned approach

Add a goroutine-safe job queue so background work can post results back to the JS runtime without reentering WASM unsafely.

### Mechanism (sketch)

1. **Per-runtime job channel**: each `JSRuntime` owns a `chan jsJob` (buffered, size ~64).
2. **QuickJS interrupt handler**: install `JS_SetInterruptHandler` so the runtime polls periodically. QuickJS calls this every N instructions; it can be used to drain the job channel.
3. **Job shape**:
   ```go
   type jsJob struct {
       resolve func(*qjs.Context)  // runs on the JS thread, safe to call Resolve
       reject  func(*qjs.Context)
   }
   ```
4. **Async function body**: spawns a goroutine that does the blocking work, then enqueues a job carrying the resolver/rejecter closures. The job, when drained by the interrupt handler, executes on the JS thread.
5. **Yield points**: the runtime must periodically hit the interrupt handler. Eval with `FlagAsync` already yields on await; for synchronous handlers, an explicit `await Promise.resolve()` at extension-defined checkpoints would force yields.

### Alternative: separate-process QuickJS

If the interrupt-handler route proves too invasive, run QuickJS as a subprocess (one per session) communicating via stdin/stdout (JSON-RPC or msgpack). This sidesteps the threading issue entirely — Go talks to a real Unix process, not a WASM module in-process. Trade-off: harder to bridge rich Go types into JS, and startup cost.

## Scope of changes

- `packages/coding-agent/src/core/extensions/js_runtime.go`: add job channel + interrupt handler wiring
- `packages/coding-agent/src/core/extensions/js_context.go`'s `buildJSUI`: switch the synchronous-body pattern back to the goroutine pattern, with goroutines now enqueueing jobs instead of calling `Resolve` directly
- `js_ui_async_test.go`: extend with cases that verify resolution happens correctly under contention (multiple concurrent ui.* calls, slow widget, etc.)
- Decide on the yield-point contract — do extension authors need to opt in, or does the runtime yield automatically?

## Open questions

- Does `fastschema/qjs` expose `SetInterruptHandler`? If not, can we fork or move to a fork that does (`nicolo-ribaudo/qjs` or similar)?
- Will draining a job channel during an interrupt handler cause re-entrancy issues if a job itself triggers more JS execution?
- Should we migrate to `rogchap.com/v8go` (V8 via CGO) instead of investing in the qjs job queue? V8 has proper threading but adds CGO + larger binary.
- Does the synchronous-body pattern have any correctness issues we should document as known limitations instead of fixing?

## Workaround in the meantime

Until 0.1.1 ships, the synchronous-body pattern is the supported model. Documented in `js_context.go`'s `buildJSUI` header comment. JS extension authors should treat their handlers as single-threaded and avoid background work that needs to call back into JS.
